# 模板内存热区画像与恢复预热

## 1. 一句话方案

构建流程新增一个开关(`CUBE_TEMPLATE_PROFILE_ENABLE`,默认关闭)。打开后,模板快照落盘时**不急着报成功**:先从新模板按正常 fast-restore 路径起两个一次性的校验沙箱,记下 guest 从恢复到就绪这段时间实际触碰的内存页,两轮取交集,把结果作为 extent 清单随模板一起保存——之后才把构建标记为成功。

此后,每个从这个模板启动的沙箱在 restore 时都会检查有没有画像:有,就把这些区域精确预读进 page cache,guest 首次触页命中内存而不是卡在磁盘读上;没有,行为与原始行为逐字节一致。预热是纯优化:任何环节出问题都只是退回原行为,绝不会阻断模板发布或沙箱创建。

## 2. 背景:冷启动为什么慢

fast-restore 把模板内存文件 `MAP_PRIVATE` 映射进 VMM。之后 guest 每次首次触碰一页,都是一次真实的磁盘读:

- **热态**(文件已在 page cache):缺页命中内存,启动延迟与磁盘无关;
- **冷态**(机器重启或大量内存回收后,cache 全空):每次缺页都阻塞在 NVMe 读上,磁盘 I/O 成为冷启动延迟的主导项。

一个结构性条件让这件事非常可解:同一个模板的所有沙箱映射的是**同一个共享 inode**("share map memory file"),page cache 天然跨沙箱共享。把这一份文件的热区灌进 cache 一次,这台节点上之后的所有沙箱——不管并发多少——都直接受益。

## 3. 原理:画像启动集,再按图预热

- **画像**。guest 加载一页的前提是触碰它,所以校验沙箱从 restore 跑到 ready 之后,VMM 进程里内存文件映射上标记为 *present* 的页,恰好就是"一次启动会加载的页"。读 `/proc/<pid>/{maps,pagemap}`,沿映射逐页走一遍,把虚拟地址换算回文件偏移(§4.2)——不需要任何 VMM 内部知识。
- **为什么要两轮**。连续两轮 restore 各画像一次,只保留两轮都出现的页。两轮触页集高度重合——启动要加载什么是非常可复现的——交集同时剔除了单轮偶发触页(抖动)。
- **启动集长什么样**。启动热区只占内存文件的一小部分,而且大头并不集中在文件头部。此前尝试过"固定头部窗口预读",只能覆盖小部分热点,这是"必须按画像预热、固定窗口行不通"的依据。
- **预热**。对每个 extent 发一次 `posix_fadvise(POSIX_FADV_WILLNEED)`——异步、立即返回。热区体量小,顺序读开销在几十毫秒量级,而且与设备恢复、guest 启动并行;高并发创建时第一个沙箱把 cache 灌热,后面的几乎是空操作。
- **为什么必须精确**。把整个文件(GB 级)预读一遍实测反而更糟:预读 I/O 和上百路并发缺页流抢 NVMe 队列,热点页被排到冷页后面,结果比不预热还差。精确是这件事成立的前提。

## 4. 集成设计

### 4.1 总览:构建期生产,运行期消费

```
 模板构建流程(生产侧;每次构建一次;受构建开关控制,默认关闭)
 ────────────────────────────────────────────────────────
 create snapshot 成功(内存卷 + VM 状态落盘)
   ├─ 开关未开(默认)→ 模板 ready → 通知用户
   └─ 开关打开 → 模板状态 = 构建中(先不通知用户),进入画像阶段:
        ├─ 第 1 轮:从模板按正常 create 路径起一个一次性校验沙箱,
        │           restore → ready → 读 pagemap → 销毁
        ├─ 第 2 轮:再来一遍(第 1 轮已灌热 cache,更快)
        ├─ 两轮页集取交集 → 合并为 extent → 原子写 hot-pages.json
        │           到快照状态目录(memory-ranges 同目录)
        └─ 模板状态 = ready → 通知用户构建成功

 正常沙箱创建(消费侧;每次 restore;与构建开关无关)
 ────────────────────────────────────────────────────────
 打开内存文件后:读快照状态目录里的 hot-pages.json 并校验
   ├─ 有效 → 按 extent 逐段 posix_fadvise(WILLNEED)
   └─ 缺失/无效 → 不预读,与源方案逐字节一致
```

底线规则:**预热是纯优化**。画像路径上任何失败都退化为现有行为,绝不阻断模板发布或沙箱创建。

### 4.2 生成画像:构建末尾两轮校验性 restore

**时机**:create snapshot 成功(内存卷 + VM 状态落盘)之后、模板翻转为 ready 之前。整个窗口内用户看到的都是"构建中",画像做完才收到成功——画像耗时计入构建耗时。

**前置条件**:构建开关打开(`CUBE_TEMPLATE_PROFILE_ENABLE`,默认关闭)。开关没开时整个阶段直接跳过:快照成功 → 立即 ready,构建耗时和行为与原本完全一致,不产生画像文件。

**步骤**:

1. 先删掉已存在的 hot-pages.json——**无条件,与开关无关**。上一次构建这个模板留下的旧画像绝不能跟着重建后的模板一起发出去;
2. 第 1 轮:从全新模板走**正常创建路径**起一个校验沙箱,restore → ready;
3. 采集:读该沙箱 VMM 进程的 `/proc/<pid>/maps` 定位内存文件映射,`/proc/<pid>/pagemap` 取 present 页;文件偏移 = 映射 offset + (vaddr − 映射起始);
4. 销毁沙箱;第 2 轮重复;
5. 两轮页集取交集(页粒度),相邻页合并为 extent,原子写 JSON(临时文件 + rename)到快照状态目录;
6. 模板状态 → ready,通知用户。

### 4.3 画像文件格式与放置

```json
{
  "version": 1,
  "template_id": "tpl-xxxx",
  "mem_file_size": 2147483648,
  "profiled_at": "2026-09-20T03:00:00Z",
  "extents": [[offset_bytes, len_bytes], ...]
}
```

- 每个 extent 是**恰好两个元素的二元组** `[offset_bytes, len_bytes]`。消费端按 `[u64; 2]` 严格解析——多出任何字段(哪怕第三个元素)都会让整个文件解析失败,降级为不预热并记 debug 日志。v1 消费端**不读任何其他字段**;
- 文件放在模板包的快照状态目录里,`memory-ranges` 旁边(`<模板包>/metadata/snapshot/hot-pages.json`)。这个目录就是 restore 时 VMM 已知的 `source_url`,不需要额外传任何参数。语义上它是模板元数据的一部分,跟随模板生命周期:模板删除它随之删除,模板重建时先删后写;
- **分发是免费的**:画像随快照包 metadata 走,不需要新打包逻辑。XFS 后端 metadata 就是本地目录(模板包节点本地,"分发"就是各节点自己构建);S3 后端画像在 metadata 卷封存(finalize)之前写入、随卷一起走——restore 挂载 metadata 卷后,同样的相对路径直接可见;
- **校验规则**(消费侧;任一不满足 → 无效 → 不预热,回退行为):version 可识别、`mem_file_size` 与实际文件一致、extent 不越界、总量不超过内存大小的 50%(防失控)。把旧画像挡在外面是生产侧的职责:构建在阶段开始前无条件删除,`mem_file_size` 一致性加 schema version 兜底;

### 4.4 消费画像:fast-restore 路径上的一个挂点

fast-restore 分支(memory_manager.rs `new_from_snapshot`,fast_restore 下 `open_read()`)打开内存文件后直接 mmap。消费侧就插在这里:

```
打开内存文件后:
  读快照状态目录里的 hot-pages.json 并校验
    ├─ 有效:按 extent 逐段 posix_fadvise(WILLNEED)——异步、立即返回
    └─ 缺失/无效:不预读,与原本逻辑完全一致
```

- fadvise 在读完成之前就返回,预热与设备恢复、guest 启动重叠,不占 restore 关键路径;
- **seccomp 前提**:vmm 线程白名单(seccomp_filters.rs)原本没有 `fadvise64`。现在通过具名常量 `SYS_FADVISE64` 放行(x86_64 用 `libc::SYS_fadvise64`;aarch64 libc 不导出该常量,用 asm-generic 系统调用号 223);
- 高并发创建时,所有 create 对同一个共享 inode 发 fadvise,内核在 page cache 层合并重复读,实际 I/O 约等于一份热区;

### 4.5 兜底与兼容性保证(硬性要求)

生产路径是**纯消费者**(只读),生成只存在于构建流程。兜底路径就是默认行为本身(不预读):

| 场景 | 行为 |
|---|---|
| 存量模板 / 开关未开时构建的模板(默认)/ 画像阶段失败 / 新分发节点缺画像文件 | 无画像,**与原本路径完全一致**;生产路径也不会自行补偿生成 |
| 画像缺失/损坏/校验不过 | 同上,记 debug 日志 |
| 校验 restore 失败 / 阶段超时(60s 上限) | 跳过画像,**模板照常标记成功**(无画像),记 warn——画像失败绝不阻断发布 |
| 上一次构建留下的旧画像 | 构建在阶段前**无条件**删除,开关开着或关着都一样(§4.2) |
| 校验沙箱清理失败 | 构建流程重试销毁;残留交给常规沙箱回收机制 |
| fadvise 失败(任一 extent) | warn + 跳过该段,restore 继续 |
| 采集失败(pagemap 读失败 / 写盘失败) | 同阶段失败:模板照常 ready,无画像 |
| 消费开关禁用 / 构建开关未开 | 消费侧什么都不读 / 生产侧什么都不生成;各自完全回到原始路径|
| UMA / 旧配置 / 版本回滚 | 没有画像文件就没有行为差异;旧版本眼里它是个不可见的旁路文件 |

不变式:**模板发布和沙箱创建绝不能因为画像相关的原因失败或可感知地变慢**(消费侧校验是纯内存判断;生产侧失败一律 fail-open)。不新增 API,不改前端;模板状态复用既有"构建中 → ready"语义,只是翻转得晚一点。

### 4.6 配置开关

| 变量 | 默认 | 含义 |
|---|---|---|
| `CUBE_VMM_RESTORE_HOTSET_DISABLE` | 未设置 | `1`/`true`:消费侧不读画像(restore 路径完全回到原始路径) |
| `CUBE_TEMPLATE_PROFILE_ENABLE` | 未设置(**默认不生成**) | `1`/`true`:构建末尾执行两轮画像;未设置:构建流程与原始路径完全一致(无画像阶段、无额外耗时) |
| `CUBE_TEMPLATE_PROFILE_TIMEOUT_SEC` | 60 | 画像阶段(两轮)总超时;超时按 §4.5 处理(仅构建开关打开时生效) |

## 5. 设计决策

1. **两轮 + 交集是当前定稿**(构建管线内从快照 resume 画像):交集剔除单偶发触页。
2. **只画像真实 restore 触碰的页。** 快照时刻的触页集是"从零 boot + 定制"的超集,定制越重越脏;两轮校验 restore 还顺带当了 restore 质检。
3. **生产侧与消费侧完全解耦。** 生成在构建流程(控制器侧 /proc 采集,零 shim 改动);消费在 shim/VMM(JSON + seccomp,约 150 行)。生产沙箱零新增写路径。
4. **生成默认关闭、显式打开。** 预热拿构建时间换,这笔账按部署、按模板各不相同。默认关闭保证存量构建流程零影响,按批次打开。消费侧不关心这个开关——有画像就预热。
5. **page cache 只有一份。** 预热 I/O 落在发起线程所在的节点,跨节点访问本来就是内存速度——不为局部性做 per-node 缓存副本。
6. **预热是 cache 操作,不是拷贝。** 不写任何沙箱文件、不产生 CoW;reflink/共享页在被写之前始终共享同一个 cache 页。
7. **cache 被回收只会退化,不会更糟。** 预热和 create 之间 cache 被回收,就退回逐页缺页——基线。
